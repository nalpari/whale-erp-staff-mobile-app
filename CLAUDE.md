# CLAUDE.md

## What this is

A Flutter (Android + iOS only) WebView shell for the staff mobile web app `whale-erp-new-staff` (Next.js, sibling repo `../whale-erp-new-staff`; older notes call it `whale-erp-staff`). The app itself has almost no UI: it loads the web app full screen and adds native glue (back button, external links, pull-to-refresh, error/retry, splash). Bundle ID `kr.co.whaleerp.staff`, display name 「웨일ERP 직원」, iPhone only (`TARGETED_DEVICE_FAMILY = "1"`), portrait only.

## Architecture

Everything lives in `lib/main.dart`, except the JS bridge in `lib/native_bridge.dart`, location measuring in `lib/location_reading.dart` and file downloads in `lib/file_download.dart`. The bridge is injected only into the `WEB_URL` origin's main frame (`javaScriptBridgeOriginAllowList` + `javaScriptBridgeForMainFrameOnly`): on Android the plugin computes the caller's origin and isMainFrame in page JS, so an iframe could spoof them; `NativeBridge.handle` re-checks as a second layer.

- `NativeBridge` (`lib/native_bridge.dart`) registers JS handlers in `onWebViewCreated`. Every call goes through `handle()`, which answers `{ok: false, error: 'forbidden'}` unless the call is from the main frame of an `isTrustedOrigin` page (https, same host and port as `WEB_URL`), and wraps results as `{ok: true, data}` or `{ok: false, error: 'failed'}` (exceptions are reported, never thrown to JS). Unknown handler names never reach Dart; the plugin returns `null`. The contract for the web side is `docs/native-bridge.md`; add new handlers there too. First handler: `appInfo` (`version`, `platform`).
- `deviceId` (bridge handler, plan decision 9): a native channel (`kr.co.whaleerp.staff/device`, `MainActivity.kt` / `AppDelegate.swift`) returns SHA-256 of `whale-staff-device:` + Android `ANDROID_ID` / iOS `identifierForVendor` as 64 lowercase hex chars; the raw value never leaves native code. The Dart handler has a 2 s limit and answers `failed` unless the value matches that format; the web login then falls back to its cookie UUID. On Android 8+ `ANDROID_ID` depends on the signing key, so a debug/locally signed build (each developer's debug key differs too) and the Play-signed store build give different values on the same device; sessions made with one stay until they expire. On Android it is only returned when the webview supports `DOCUMENT_START_SCRIPT` (`nativeGuarded`): only then does the plugin pin the bridge script natively to the `WEB_URL` main frame, so on older webviews the long-lived ID is not handed out (the bridge's Java object also checks a per-webview `bridgeSecret` that only the main-frame script holds).
- `pullToRefresh` (app-internal bridge handler, never called by web screens): `pullToRefreshGuardScript` (main-frame `UserScript` at document start) calls `pullToRefresh(false)` while a visible signature pad (`.touch-none` or inline `touch-action: none`, hidden ones such as inside a closed dialog or with `visibility: hidden` do not count) is in the document, watched with a `MutationObserver` on all attributes (so a modal hidden by e.g. `data-state` plus CSS is re-checked) and re-synced on a back-forward-cache `pageshow`, so the first fast stroke from the top is not grabbed by `SwipeRefreshLayout` before an async bridge call lands; it also turns it off while a finger is down on an element whose own or ancestor `touch-action` is `none`, and back on when neither holds; `onLoadStart` turns it back on when a new document starts (not `onLoadStop`, which fires after sub-resources finish and would undo a guard the user started while images were still loading; in-page navigation relies on the next finger lift). Not verified on a real device that the first fast stroke is caught before Android's swipe-refresh takes it.
- `measureLocation` (`lib/location_reading.dart`, bridge handler of the same name) runs the shared `LocationGate` permission check (same guide snackbars as the geolocation prompt), then takes the first fresh fix from `Geolocator.getPositionStream` (high accuracy, 8 s limit; never last-known, and fixes timestamped more than 2 s before the call are skipped because the OS may hand back a cached fix first: `firstFreshPosition`); with approximate-only access it takes the OS's first fix instead (`readAnyPosition`, Android refreshes coarse fixes rarely) and every ok result carries `ageSeconds` and returns coordinates, accuracy, `isMocked` and whether access is precise from that one reading (plan decision 8). The web waits 75 s for this call: the permission check is capped at 60 s overall (`permissionTimeout`), measuring at ~9 s, and the follow-up reads (accuracy, permission, service) at 2 s each, ~73 s worst case. On Android `callAsyncJavaScript` (used to wait for the first paint before hiding the splash) answers through the bridge, so it has a 2 s timeout now that the bridge is only in the `WEB_URL` main frame. Mock detection was verified on the emulator with a shell test provider (`appops set com.android.shell android:mock_location allow`, `cmd location providers add-test-provider gps`, `set-test-provider-location`).
- File downloads (plan decision 10): the payslip PDF (`/pay/<id>/pdf`, same-host attachment behind httpOnly cookies) arrives in `onDownloadStarting`; only when `isTrustedOrigin(url.origin)` does the app copy the webview cookies (`CookieManager.getCookies`) into its own `HttpClient` request. Redirects are followed by hand (`followRedirects = false`, at most `maxDownloadRedirects`) and the cookie is sent only while the hop is `isSameOrigin` with the first URL: the built-in redirect only drops cookies on a host change, so a same-host other-port or http hop would carry them. Redirect hops must be same-origin with the first URL or an S3 signed URL (`isSignedDownload`); anything else fails. Bodies are capped (`maxFileBytes` 50 MB, `maxMessageBytes` 64 KB) and by a total `downloadBodyTimeout` (60 s, the subscription is cancelled); the body is written chunk by chunk through a `RandomAccessFile`, pausing the response while each write runs, so slow storage never piles data up in memory and write errors fail the download besides the 15 s idle limit; a partial file is deleted. A signature query with an empty value is not a signed URL. When the app opens a download's HTML answer in the webview (`_openingInWebView`), that one navigation is not intercepted again even if it is the payslip PDF route (the mark is cleared on the next load stop or main-frame error, and expires after 5 s, because Android does not call `shouldOverrideUrlLoading` for `loadUrl`). Cookies set by a same-origin redirect response (`Set-Cookie`, e.g. a login refresh) override the webview cookies on the following hops (`mergeCookies`), only where their `Path` applies (`cookiesFor`); expired ones are dropped. On a body timeout or error the in-flight disk write is awaited before the caller closes and deletes the partial file. Main-frame navigations to the same-origin `/pay/<id>/pdf` route (`isPayslipPdf`) are cancelled in `shouldOverrideUrlLoading` and downloaded by the app, so the PDF is generated only once and an older web build's plain-text 404/409/502 failure never covers the page. The current web (branch `magmar`) answers a failure with a 3xx (Next `redirect()`, 307) to the payslip detail `/pay/<id>?download=notfound|reviewing|failed` (or `/pay` for a bad id, which is not a failure page and still counts toward the 15 s repeat check), which the app opens in the webview; a login redirect is handled the same way. Download errors are reported with URL queries stripped (`redactUrls`) so S3 signatures never reach the logs, and the share sheet gets a `sharePositionOrigin` (needed for the iPad popover). The contract file route 302s to an S3 signed URL; `shouldOverrideUrlLoading` cancels navigations where `isSignedDownload` (https, `*.amazonaws.com`, a signature query) and downloads without cookies. `downloadFile` saves under a fresh temp folder with the `Content-Disposition` name (api sends `filename*=UTF-8''…`) and the result opens in the `share_plus` share sheet; `text/plain` failures are shown as the message. A 200 HTML (e.g. login redirect) is opened in the webview at the final URL it came from, only for cookie (same-origin) downloads; if the same download comes back as HTML again within 15 s the app stops and asks the user to reopen the app (app and webview cookies disagree), except the payslip failure page (`isPayslipFailurePage`), which is opened and clears the repeat record (`openInWebViewGuard`, unit-tested). Any other HTML (502 pages, S3) is a failure. Limits: connect through response headers 30 s, body 15 s idle, cookie read 5 s. iOS sends a main-frame error after the plugin cancels a PDF response, so main-frame errors for the intercepted URL within 3 s are ignored (other pages' errors still show the error screen). `isSignedDownload` only accepts S3 hosts (`s3.amazonaws.com`, `*.s3[.-]<region>.amazonaws.com`), not other AWS services. Responses whose body is not needed (200 HTML, non-200) return on headers without reading the body. `download-*` folders older than 10 min (`keepDownloadsFor`) in the shared temp dir are removed before each download; newer ones are kept because the share sheet may still be reading them (the download lock is released before sharing). The cookie is looked up again for every same-origin redirect hop (`cookieFor`) so cookie `Path` scoping matches the webview. Download tests use a real local `HttpServer`, so they live in `test/file_download_test.dart`: in a file with `testWidgets` the test binding turns every HTTP request into a 400.
- `isInApp(uri, base)` is the navigation rule: same host as `WEB_URL` over http(s), or webview-internal schemes (`about`, `data`, `blob`, `javascript`), stay in the webview. Everything else (other hosts, `tel:`, `mailto:`) is cancelled in `shouldOverrideUrlLoading` and opened with `url_launcher` externally. It, `isTrustedOrigin` (now in `native_bridge.dart`), `ensureLocationAccess`, `LocationGate`, `LocationAccess.allowsWeb`, `locationGuide`, `allowGeolocation`, `appUserAgent`, `readAppVersion` and `flushCookies` are the unit-tested functions (`test/widget_test.dart`); the webview itself is not testable in widget tests.
- Location: Android declares `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION`; iOS has `NSLocationWhenInUseUsageDescription`. When the page calls `navigator.geolocation`, Android routes it to `onGeolocationPermissionsShowPrompt`, which allows only `isTrustedOrigin` (https, same host as `WEB_URL`) and asks the OS permission via `geolocator` (`allowGeolocation` -> `ensureLocationAccess`), with `retain: false` (the webview does not store the grant, so each page load re-checks). `ensureLocationAccess` returns a `LocationAccess`: `precise`, `approximate` (Android 12+ "approximate" grant), `serviceDisabled` (device location off), `denied`, `deniedForever`, `failed` (error or timeout while checking/requesting). The web is allowed for the first three. If an approximate grant already existed, it re-requests once per app run so Android offers the upgrade-to-precise dialog, but not right after the user just picked approximate in the same flow; a failed re-request stays `approximate`. Each platform call has its own 60 s limit because geolocator on Android never completes if the permission dialog is interrupted (empty result); the limit also counts time the user spends deciding (known limitation). After the permission is granted, a failure to read service status or accuracy is treated as on/precise. `LocationGate` serialises requests: concurrent ones share one in-flight future (overlapping geolocator requests lose results), only the starter shows guidance, and `askPrecise` stays off after the first re-request. For `approximate`, `deniedForever`, `serviceDisabled` and `failed` a SnackBar (`locationGuide`) explains and, except for `failed`, offers app or location settings; if they cannot be opened a fallback text says where to go. Guidance that arrives while the splash is up (`_loaded` false) is held and shown in `_markLoaded`. The SnackBar sets `persist` to `MediaQuery.accessibleNavigationOf(context)`: an action would otherwise keep it on screen over the web's bottom Dock, but screen-reader users need time to reach the button. iOS has no equivalent hook in flutter_inappwebview: WKWebView asks the OS (and shows its own per-site prompt) itself, so `isTrustedOrigin` is **not** enforced on iOS. Per plan decision 8 the in-app check-in gets coordinates from the `measureLocation` handler instead (web PR #90/#91); the web falls back to `navigator.geolocation` only in an older app build without that handler, so in this build the geolocation path above is a safety net in case the web calls it anyway.
- Cookies: on Android, `flushCookies` calls `CookieManager.flush()` when the app becomes inactive or hidden (`AppLifecycleListener.onInactive` and `onHide`: home, app switch, and recents, where some launchers only pause the app (inactive) before it is swiped away; both verified on the emulator. Swiping away has no callback of its own and relies on that earlier flush). It goes through the app's own channel `kr.co.whaleerp.staff/cookies` in `MainActivity` (handled on a background task queue, because `flush()` blocks until the disk write ends and `onInactive` also fires for the notification shade or permission dialogs), which flushes and answers at once: the plugin's flush (`flutter_inappwebview_android` 1.2.0-beta.3) never answers, which left a pending reply in the engine on every backgrounding. The call waits at most 2 s and any error or timeout is only reported. The plugin already flushes on every `onPageFinished`; what this covers is cookies set after the page loaded (fetch / SPA navigation, e.g. the `Set-Cookie` on the web's login server action response, followed by a client-side redirect), which the Android webview otherwise keeps in memory, so a kill right after login could drop the auto-login cookie. iOS (WKWebView) persists cookies itself and the plugin has no flush there.
- `WebScreen` wraps the `InAppWebView`: `PopScope` maps Android back to: close the topmost open web `<dialog>` (`closeTopDialogScript` dispatches a cancelable `cancel` event, which the web bottom sheet's `onCancel` handles with `preventDefault` + its own close; a plain dialog nobody handled is `close()`d), else webview history, else `SystemNavigator.pop()`. "Topmost" is the most recently opened one: `dialogOrderScript` (a main-frame `UserScript` at document start) wraps `HTMLDialogElement.prototype.showModal`/`show` to stamp `data-whale-opened-at` only when the call actually opens a closed dialog, because `querySelectorAll` returns DOM order; unstamped dialogs fall back to DOM order. Open modals (`:modal`) are chosen before non-modal dialogs, since a modal sits on top. The script runs with a 1 s timeout: a script error falls through to the normal back, but a timeout consumes the press (the script is not cancelled and may still close the sheet, so navigating too would do two things on one press). If the next press comes within 10 s of a timeout, the script is skipped and the normal back runs, so a hung webview cannot make back useless. The bypass only applies on the same page: `onUpdateVisitedHistory` (fires for SPA navigation too) bumps `_page` and clears it, and a late timeout from an older page does not set it. A late answer from the timed-out script clears the bypass (the webview is alive, so the remaining sheet is checked again), and `_back` stops if the page changed while the sheet check was running. A main-frame load error (except `CANCELLED`) shows `_ErrorView`. User-Agent gets `WhaleStaffApp/<version>` appended (`appUserAgent`, version from `package_info_plus` read in `main()` before `runApp` via `readAppVersion`, which falls back to `unknown` on error, an empty version, or a 2 s timeout because `main()` holds the first frame while it waits) so the web app can detect the shell. It is for detection only, never for authorization.

### Two-stage splash (the subtle part)

The OS splash (generated by `flutter_native_splash`) is static, so `SplashOverlay` draws an identical screen in Flutter on top of the webview while the first page loads, then fades out. The handoff only looks seamless if these invariants hold:

- `splashColor`, `splashLogo`, `splashLogoSize` in `main.dart` must match the `flutter_native_splash` block in `pubspec.yaml`. The 720px `assets/splash_logo.png` is treated as 4x by the package, hence 180dp. The overlay sits outside `SafeArea` so it is centered on the full screen like the OS splash.
- `main()` calls `deferFirstFrame()` and `SplashOverlay` calls `allowFirstFrame()` only after `precacheImage`, so the first Flutter frame never shows the background without the whale.
- `MainActivity.kt` removes the Android 12+ system splash with no exit animation (`setOnExitAnimationListener { it.remove() }`); the default animation fades the icon out first and breaks the handoff.
- The overlay hides only after `onLoadStop` plus two `requestAnimationFrame`s inside the page; `onLoadStop` alone fires before the page paints and exposes a blank white webview.
- There is no loading indicator on the overlay (removed 2026-11-20 at the user's request); it is the static whale until the page paints. An earlier spinning ring had to be added only after the webview attached (`onWebViewCreated` + `endOfFrame`), because rendering it before the platform view joined composition caused one-frame flashes on the emulator. Keep that in mind if an indicator comes back.
- `AnnotatedRegion` sets light status-bar icons over the indigo overlay and dark icons over the web content.

### Image assets

Design: white whale on indigo `#4C4DDC` (= `primary`). The chosen originals (candidate set A, 2026-11-20) live in `assets/source/` (`icon-a.png`, `splash-a.png`, `fg-solid.png`); they are not bundled (only `splash_logo.png` is listed under `flutter: assets`). Their painted backgrounds are slightly noisy and a touch off `#4C4DDC` (about `#4849DA` / `#4A4BD5`), so the solid colors in `pubspec.yaml` use `#4C4DDC`. The derived PNGs were produced with one-off Python/PIL scripts that are not in the repo:

- `app_icon.png` is `icon-a.png` copied as is.
- `splash_logo*.png`: alpha from the projection of each pixel onto (white − splash background color), RGB white, whale + stars cropped to their bounding box, scaled so the box diagonal is 720px, centered.
- `app_icon_foreground.png`: `fg-solid.png` with alpha ≤ 16 noise cleared to 0, RGB white.

| File | Use | Geometry |
| --- | --- | --- |
| `splash_logo.png` | OS splash + Flutter overlay | 720px, whale + stars box diagonal = 720px |
| `splash_logo_android12.png` | Android 12+ splash icon | 1152px canvas, same 720px-diagonal logo centered (inside the 768px masked circle) |
| `app_icon.png` | iOS icon, Android ≤7 legacy icon | 1024px, background filled, whale 60% width |
| `app_icon_foreground.png` | Android adaptive foreground + monochrome | 1024px transparent, whale 49% width (diagonal ≈ 66dp of 108dp) |

Because the foreground PNG already includes the 108dp safe-zone padding, `adaptive_icon_foreground_inset: 0` disables the package's default 16% inset.

## Dependency pins

`flutter_inappwebview` is pinned to `6.2.0-beta.3`: the 6.1.5 stable Android implementation uses `proguard-android.txt`, which AGP 9 (used by this template) rejects. Overriding only `flutter_inappwebview_android` breaks the Windows implementation via the shared platform interface, so the whole family is on the beta. Move to `^6.2.0` once stable ships.
