# 앱 ↔ 웹 브리지 약속

웹(`whale-erp-new-staff`)이 앱 기능을 부르는 방법이다. 앱 쪽 구현은 `lib/native_bridge.dart`, 웹 쪽은 `src/lib/native-bridge.ts`(웹 PR #87. 브리지 장애 때 다시 시도는 판정이 `src/lib/device-location.ts`, 화면이 `src/app/(app)/check-in/check-in-screen.tsx` · 웹 PR #91. 로그인의 `deviceId` 는 `src/app/(auth)/login/login-form.tsx`)에 둔다. 한쪽을 바꾸면 이 문서와 다른 쪽을 같이 고친다.

## 앱 안인지 알아보기

- 앱은 기본 User-Agent 끝에 공백 하나를 두고 `WhaleStaffApp/<앱 버전>`을 붙인다(예: `... Mobile Safari/537.36 WhaleStaffApp/1.0.0`).
- 웹은 User-Agent **맨 앞이나 공백 바로 뒤**에 온 `WhaleStaffApp/`만 앱으로 본다(`NotWhaleStaffApp/1.0` 같은 다른 제품명은 앱이 아니다). 표식이 여럿이면 마지막 것을 버전으로 쓴다. 예전 표식 `WhaleERPStaffApp`은 앱으로 보지 않는다.
- 웹은 이 값으로 **앱 안인지 판별만** 한다. 권한 확인에 쓰지 않는다(누구나 흉내 낼 수 있다). 실제 허락은 앱이 출처와 맨 위 화면인지로 정한다.

## 브리지 준비

- 브리지가 준비되면 window에 `flutterInAppWebViewPlatformReady` 이벤트가 온다.
- 웹은 `window.flutter_inappwebview.callHandler`가 **함수로** 있으면 부를 수 있다고 본다. Android는 함수가 보여도 웹뷰가 문서 시작 스크립트를 지원하지 않으면 준비 이벤트 전에는 부를 수 없어서, 플러그인이 준비 이벤트 때 남기는 `window.flutter_inappwebview._platformReady === true`까지 본다. iOS는 이 표시가 없어도 함수가 보이면 부른다.
- 준비 이벤트는 한 번만 온다. 그래서 웹은 루트 레이아웃 `<head>`의 짧은 인라인 스크립트로 문서를 읽기 시작할 때부터 이벤트를 듣고, 이벤트가 올 때마다 그때의 브리지 객체를 `window.__whaleBridgeReady`에 남긴다(웹 PR #91). Android에서는 지금 브리지가 그 객체와 같으면 준비된 것으로 본다(브리지가 바뀌면 새 것은 다시 확인).
- 앱 안인데 준비가 안 됐으면 웹은 준비 이벤트를 **3초** 기다린다. 기본은 이벤트가 오지 않아도 그때 `callHandler` 함수가 있으면 불러 본다. 그래도 없으면 `unavailable`로 끝내고 웹 콘솔에 남긴다(앱 밖에서 열었을 때와 구분하려고).
- 예외(엄격 대기, `strict`): 출퇴근 위치(`measureLocation`)와 「다시 시도」 버튼의 연결 확인은 Android에서 준비 표시(이벤트 · `_platformReady`)까지 있어야 부른다. 3초씩 **두 번**(최대 6초) 기다려도 준비되지 않으면 부르지 않고 「앱 연결이 잠깐 안 됐습니다」와 「다시 시도」 버튼을 보인다. 브라우저 위치로는 넘기지 않는다(모의 위치 판정이 빠지므로). 다시 시도는 연결만 확인하고 위치는 읽지 않는다(2026-11-24 창수).
- 앱 쪽에서 할 일은 없다. 플러그인(`flutter_inappwebview`)이 이벤트와 표시를 남긴다. 앱은 기능을 `onWebViewCreated`에서 등록해 페이지 스크립트보다 먼저 준비한다.

## 부르기

```js
const result = await window.flutter_inappwebview.callHandler("appInfo");
```

- 웹은 `callHandler`를 `src/lib/native-bridge.ts` 밖에서 부르지 않는다. 화면은 `callNative` · `getAppInfo` 같은 함수만 쓴다.
- 인자는 `callHandler(이름, ...인자)`로 넘긴다. JSON으로 바꿀 수 있는 값만 넘긴다.

## 답

앱은 언제나 아래 셋 중 하나로 답한다.

| 모양 | 뜻 |
| --- | --- |
| `{ ok: true, data: ... }` | 성공. **`data` 칸은 늘 넣는다.** 돌려줄 값이 없어도 `data: null`로 넣는다 |
| `{ ok: false, error: "forbidden" }` | 앱이 받지 않는 호출. 웹 주소와 다른 출처(https · 호스트 · 포트), 또는 맨 위 화면이 아닌 곳에서 불렀다. 앱은 브리지를 웹 주소의 맨 위 화면에만 심으므로(iframe 에는 `callHandler`가 없어 웹은 `unavailable`을 받는다) 보통은 나오지 않는 2차 방어다 |
| `{ ok: false, error: "failed" }` | 앱 기능이 실패했다. 자세한 내용은 앱 로그에만 남는다 |

웹은 앱의 답을 아래 네 가지 실패로 나눠 다룬다.

| 웹이 받는 실패 | 언제 |
| --- | --- |
| `forbidden` | 앱이 `forbidden`으로 답했다. 웹 코드 버그이거나 다른 사이트가 부른 것이라 다시 시도하지 않는다 |
| `failed` | 앱이 `failed`로 답했거나, 호출이 예외로 끝났거나, **10초 안에 답이 없었다** |
| `unavailable` | 앱 밖이거나, 브리지가 없거나, 앱에 없는 기능이다. 앱에 없는 이름으로 부르면 앱까지 오지 않고 `null`이 돌아온다(웹뷰 플러그인 동작) |
| `malformed` | 앱의 답이 위 표와 다르다(`data` 칸이 없음, 모르는 오류 코드, `data` 모양이 기능 약속과 다름) |

## 같은 출처 iframe (웹이 지킬 것)

앱은 브리지를 웹 주소(`WEB_URL`)의 맨 위 화면에만 넣고, 다른 출처의 iframe에서는 `callHandler`가 아예 없다. 하지만 **같은 출처**의 iframe은 브라우저 규칙상 맨 위 화면의 JS(`window.top.flutter_inappwebview`)에 접근할 수 있어서, 앱은 그 호출을 맨 위 화면에서 온 것과 구분하지 못한다. 그런 iframe 안에서 믿을 수 없는 스크립트가 돌면 위치 같은 앱 기능을 불러 결과를 가져갈 수 있다.

- 웹은 `WEB_URL`과 같은 출처에서 믿을 수 없는 콘텐츠(사용자가 올린 HTML, 외부 위젯 등)를 iframe으로 띄우지 않는다.
- 꼭 띄워야 하면 다른 출처에서 서빙하거나, `sandbox`에 `allow-same-origin`을 넣지 않고 띄운다. 그러면 iframe이 다른 출처로 취급돼 브리지에 닿지 못한다.
- 2026-11-23 현재 웹에 같은 출처의 외부 콘텐츠 iframe은 없다(주소 검색의 Daum 우편번호는 다른 출처).

## 시간 제한 (앱 기능을 만들 때 지킬 것)

- 웹은 호출마다 **10초**까지 기다리고, 넘으면 `failed`로 끝낸다. 앱이 그 뒤에 답해도 버려진다.
- 그래서 오래 걸릴 수 있는 기능은 **앱 안에서 10초보다 짧게 끝나도록** 시간 제한을 걸고, 넘으면 `failed`나 기능별 결과로 먼저 답한다.
- 예외: 사용자가 OS 창을 보고 고르는 동안 기다려야 하는 기능은 기능 목록에 웹이 기다릴 시간을 따로 적고, 앱은 그보다 짧게 끝낸다(`measureLocation`: 웹 75초).
- 시간 초과는 웹이 기다리기를 그만둔 것일 뿐 앱 기능은 계속 돌 수 있다. 부작용이 있는 기능(파일 저장 등)을 웹이 다시 부르면 두 번 실행될 수 있으니, 그런 기능은 다시 부르기 전에 결과를 따로 확인하게 만든다.

## 기능 목록

| 이름 | 인자 | `data` | 쓰는 곳 |
| --- | --- | --- | --- |
| `appInfo` | 없음 | `{ version: "1.0.0", platform: "android" \| "ios" \| "other" }` | 브리지가 살아 있는지 확인, 앱 버전별로 기능 켜고 끄기. 웹은 `platform`이 셋 밖의 값이면 `malformed`로 본다 |
| `measureLocation` | 없음 | 아래 「measureLocation」 | 출퇴근 탭 지도와 출근 · 퇴근 판정. 앱 안에서는 `navigator.geolocation` 대신 이것을 쓴다(계획 결정 8) |
| `deviceId` | 없음 | `{ deviceId: "<64자 소문자 16진수>" }` | 웹 로그인이 쿠키 UUID 대신 쓰는 기기 식별자(계획 결정 9). 앱은 기기 고유값(Android `ANDROID_ID` · iOS `identifierForVendor`)에 앞말 `whale-staff-device:`를 붙여 SHA-256 으로 바꾼 값만 넘기고 원래 값은 앱 밖으로 내보내지 않는다. 앱을 다시 깔아도 대체로 같다(Android 8 이상은 서명 키 · 사용자별로 정해져 공장 초기화 전까지 같고, 7 이하는 기기 · 사용자 하나에 하나. Play 앱 서명을 쓰면 Play 서명 키 기준이라 로컬 서명 빌드와 값이 다르다. iOS 는 같은 회사 앱이 하나라도 남아 있으면). 못 읽으면 `failed` — 웹은 지금처럼 쿠키 UUID 를 쓴다 |
| `pullToRefresh` | 참 · 거짓 하나 | `null` | **앱 안쪽용 — 웹 화면은 부르지 않는다.** 앱이 페이지 시작 때 심는 스크립트가, 서명 패드처럼 `touch-action: none`인 곳을 누르는 동안 앱의 당겨서 새로고침을 끄고(`false`) 손을 떼면 켠다(`true`). 인자가 참 · 거짓이 아니면 `failed` |

### measureLocation

위치 권한을 확인하고(아직 정하지 않았으면 OS 권한 창을 띄우고), 지금 위치를 **새로** 한 번 재어 좌표와 모의 위치 여부를 **같은 측정값에서** 함께 돌려준다. 마지막으로 알던 위치는 쓰지 않고, 운영체제가 첫 결과로 측정 전에 캐시해 둔 옛 위치를 주면(호출 시각보다 2초 넘게 앞선 위치) 건너뛰고 다음 위치를 기다린다. 단, 「대략적 위치」만 허락된 경우는 예외다. Android는 대략적 위치를 최대 10분에 한 번만 새로 만들어서, 새 위치를 기다리면 매번 시간 초과가 난다. 그래서 운영체제가 준 첫 위치를 그대로 쓰고, 웹은 `ageSeconds`와 `precise`로 판단한다. `data`는 웹 출퇴근 화면의 위치 상태와 같은 이름을 쓴다.

| `data.status` | 다른 칸 | 뜻 |
| --- | --- | --- |
| `"ok"` | `latitude`, `longitude`(도), `accuracyMeters`(미터 · 운영체제가 알려 주지 않으면 `null`), `ageSeconds`(그 위치를 잰 뒤 지난 초), `mocked`(참 · 거짓), `precise`(참 · 거짓 · 정확도 설정을 읽지 못하면 `null`) | 위치를 쟀다. `mocked`는 운영체제가 알려 준 모의 위치 여부(Android `isMock` · `isFromMockProvider`, iOS `isSimulatedBySoftware`). `precise`가 거짓이면 「대략적 위치」(Android 대략적 위치 · iOS 정확한 위치 끔)라 반경 판정이 틀릴 수 있다(판정은 그대로 하고, 앱이 화면 아래에 정확한 위치를 켜라는 안내를 띄운다). `null`이면 `accuracyMeters`로 판단하고, 둘 다 `null`이면 판정은 그대로 하고 정확도 안내는 하지 않는다 |
| `"denied"` | 없음 | 위치 권한 거부(영구 거부 포함, 측정 중에 권한을 빼앗긴 경우 포함). 영구 거부면 앱이 설정으로 가는 안내를 띄운다. 다시 물을 수 있는 거부와 영구 거부는 아직 나누지 않는다 |
| `"unavailable"` | `reason`: `"serviceDisabled"`(기기 위치 꺼짐) · `"permissionCheckFailed"`(권한 확인 실패) · `"permissionTimeout"`(권한 확인 전체가 60초를 넘김) · `"timeout"`(8초 안에 위치를 못 읽음) · `"error"`(그 밖의 측정 오류) | 위치를 읽지 못했다. 기기 위치가 꺼졌으면 앱이 위치 설정으로 가는 안내를 띄운다 |

- **시간:** 권한 창이 뜨면 사용자가 고르는 동안 기다린다. 권한 확인 전체(정확한 위치 재요청 포함)는 앱 안에서 60초로 끊고(`permissionTimeout`), 권한이 정해진 뒤 측정은 8초로 끊는다(최대 약 9초). 잰 뒤 정확도 · 권한 · 위치 서비스를 다시 읽는 데 최대 4초가 더 들어, 최악의 합계는 약 73초다. 그래서 웹은 이 기능만 기본 10초 대신 **`timeoutMs: 75_000`** 처럼 길게 기다린다. 권한이 이미 있으면 보통 몇 초 안에 끝난다.
- **알려진 한계:** Android는 고정밀 위치가 꺼진 기기에서 측정 중 「위치 정확도 켜기」 시스템 창을 띄울 수 있다. 사용자가 그 창을 보는 사이 8초가 지나면 `timeout`으로 답한다(다시 누르면 된다). iOS는 시간 초과 뒤에도 네이티브 측정이 위치를 하나 받을 때까지 이어질 수 있다(답만 끊긴다).
- **부작용 없음:** 다시 불러도 위치를 한 번 더 잴 뿐이다. 위치 수집 · 이용 확인자료는 웹이 지금처럼 서버에 남긴다(앱은 좌표를 저장하거나 서버로 보내지 않는다).
- **겹친 호출:** 권한 창이 떠 있는 동안 온 호출은 같은 권한 결과를 기다린다.

파일 받기(급여 PDF · 계약서)와 뒤로 가기 · 바텀시트 닫기는 브리지 없이 앱이 처리한다(브리지 변경 없음, 2026-11-23. 급여 PDF 실패 안내는 웹 라우트가 상세로 돌려보내게 바뀌었다, 2026-11-24). 다음에 붙일 기능 후보: 푸시 토큰(api 협의 뒤).
